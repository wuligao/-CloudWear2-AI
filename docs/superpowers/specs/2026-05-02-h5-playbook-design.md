# CloudWear AI H5 玩法扩展设计文档

## 1. 背景

当前 H5 已具备 AI 穿搭生成的核心能力：用户可以通过关键词或照片生成穿搭结果，结果页支持多套方案切换、保存、下载、分享、再次生成，历史页和风格档案页也已经沉淀了生成记录与偏好信息。

但当前用户感知仍偏向“填条件生成一张穿搭指南”，玩法层次较少，首页的探索动机、结果页的互动反馈、分享传播链路都还可以增强。此次扩展的目标不是重做完整产品，而是在现有生成链路上增加更容易理解、更适合 H5 传播的玩法。

## 2. 目标

### 2.1 产品目标

- 把 H5 从单一生成工具升级为“可玩、可选、可分享”的 AI 穿搭体验。
- 降低用户输入成本，让用户不必从空白表单开始。
- 强化结果页互动，让用户可以继续调优，而不是生成后就结束。
- 提升分享传播能力，让生成结果更像可转发的穿搭卡片。
- 利用已有历史记录和风格档案，为后续个性化推荐打基础。

### 2.2 本期成功标准

- 首页至少新增一组可直接点击生成的场景任务卡。
- 结果页支持对多套生成结果进行选择、反馈和快捷调优。
- 结果页提供更明确的分享海报入口或分享卡片形态。
- 新玩法优先复用现有接口、数据结构和生成流程，不引入大规模后端改造。
- 移动端首屏保持清晰，主路径不比当前更复杂。

## 3. 不做范围

本期不做以下内容：

- 完整社区内容流。
- 评论、点赞、关注关系。
- 复杂衣柜管理。
- 精准尺码推荐或真实电商下单闭环。
- 多人穿搭或情侣穿搭。
- 大规模会员权益体系。
- 需要破坏性数据库变更的功能。

## 4. 核心方向

本期推荐优先做三个玩法：

1. 场景任务卡：把“填表单”变成“点一个穿搭任务”。
2. 多套 PK：一次生成多套后，让用户挑选、反馈、继续调优。
3. 分享海报：把结果包装成适合转发的穿搭卡片。

这三个方向和当前代码已有能力最匹配，能用较小改动提升玩法感。

## 5. 玩法一：场景任务卡

### 5.1 用户价值

用户进入首页时，常常不知道该怎么描述自己的需求。场景任务卡提供预设入口，让用户直接从“我要解决什么问题”开始，而不是从“季节、天气、风格、颜色”等表单字段开始。

### 5.2 入口位置

建议放在 H5 首页主视觉下方、生成方式入口上方或附近，作为第一屏可见内容之一。

推荐模块名：

- 今日穿搭任务
- 一键生成场景
- 出门前穿什么

### 5.3 首批任务卡

建议先配置 6-8 个高频任务：

| 任务名称 | 默认场景 | 默认风格 | 默认关键词 |
| --- | --- | --- | --- |
| 30 秒通勤不出错 | 日常通勤 | 简约 / 通勤 | 清爽、利落、不随便 |
| 周五约会温柔一点 | 约会 | 法式 / 韩系 | 温柔、不甜腻、有细节 |
| 周末咖啡店拍照 | 咖啡店 | 日系 / 复古 | 显高、出片、松弛 |
| 降温也不臃肿 | 日常通勤 | 简约 | 保暖、显瘦、有层次 |
| 海边旅行三套灵感 | 旅行 / 度假 | 度假 / 法式 | 清爽、轻盈、拍照好看 |
| 面试稳重但不老气 | 办公室 | 通勤 | 得体、专业、有精神 |
| 逛街好走又好看 | 逛街 | 休闲 / 运动 | 舒适、好走、显比例 |
| 派对亮眼不夸张 | 派对 | 轻奢 / 甜酷 | 有记忆点、不过度暴露 |

### 5.4 交互流程

1. 用户点击任务卡。
2. 系统将任务卡映射为生成参数。
3. 如果用户未登录，沿用现有登录提示和跳转逻辑。
4. 已登录用户进入关键词生成页，自动填入场景、风格、地点、颜色等字段。
5. 可选：如果 URL 带 `autoGenerate=1`，直接发起生成。

### 5.5 参数映射

任务卡可以复用现有 URL 参数：

- `screen=keyword`
- `season`
- `temperature`
- `weather`
- `location`
- `occasion`
- `style`
- `colorPreference`
- `autoGenerate`

首期建议不新增接口。任务卡可以先写在前端本地配置里，后续再纳入 H5 后台配置。

### 5.6 配置化建议

短期：

- 在 H5 前端维护 `scenarioTasks` 常量。
- 每个任务包括 `id`、`title`、`subtitle`、`icon`、`preset`。

中期：

- 扩展后台 H5 配置 JSON，增加 `scenarioTasks`。
- 运营可在后台调整任务标题、排序、默认参数、是否启用。

推荐结构：

```json
{
  "id": "commute-30s",
  "title": "30 秒通勤不出错",
  "subtitle": "清爽利落，不用纠结",
  "icon": "briefcase",
  "preset": {
    "occasion": "日常通勤",
    "style": "简约通勤，清爽利落，不随便",
    "location": "办公室",
    "colorPreference": "黑白灰"
  }
}
```

### 5.7 验收标准

- 首页能看到任务卡模块。
- 点击任务卡后能进入关键词生成流程。
- 任务卡带入的参数能在生成页正确展示。
- 已登录用户可以完成生成。
- 未登录用户能看到明确登录提示，并在登录后回到对应任务。
- 任务卡不影响原有关键词生成和照片换搭入口。

## 6. 玩法二：多套 PK

### 6.1 用户价值

穿搭决策天然需要比较。一次只给一套方案时，用户很难知道“是不是最适合我”。多套 PK 可以让用户在多个结果里选喜欢的，再用反馈继续调优。

当前结果页已经有多套结果切换能力，也已有反馈文案和调优动作雏形，适合顺势强化。

### 6.2 入口位置

主要在结果页：

- 多套缩略图切换区。
- 当前大图下方。
- 保存按钮附近。

### 6.3 交互结构

结果页建议分为三层操作：

1. 选择：用户在多套结果中切换当前 LOOK。
2. 反馈：用户点“喜欢这套 / 太成熟 / 太普通 / 颜色不适合 / 想更显瘦”。
3. 调优：用户点“换成黑色系 / 更日常 / 换鞋子 / 更显瘦”等快捷动作，系统带着原参数再次生成。

### 6.4 文案建议

模块标题：

- 哪套更适合你？
- 给这套一点反馈
- 继续微调

反馈按钮：

- 喜欢这套
- 太成熟
- 太普通
- 颜色不适合
- 想更显瘦

调优按钮：

- 换成黑色系
- 更日常
- 换鞋子
- 更显瘦
- 更适合通勤
- 更适合拍照

### 6.5 数据处理

首期可以只做前端状态，不新增后端数据表：

- `selectedFeedback` 只在当前结果页短暂展示。
- 快捷调优通过 URL 参数拼接到 `style` 字段。
- 再次生成仍走现有关键词生成接口。

后续如果要做个性化，可以补充记录：

- 用户对某条结果的反馈标签。
- 用户最终保存的是哪一套。
- 用户使用过哪些调优动作。

### 6.6 与风格档案的关系

首期保存记录时，后端风格档案仍从生成记录中归纳风格、颜色、单品等信息。

后续可以把反馈标签纳入风格档案：

- 多次选择“想更显瘦” -> 推荐更强调比例的版型。
- 多次反馈“太成熟” -> 后续减少正式、老气、强通勤表达。
- 多次反馈“颜色不适合” -> 引导用户完善喜欢色和避免色。

### 6.7 验收标准

- 生成多套结果时，用户可以清楚切换当前 LOOK。
- 用户点击反馈后有即时视觉反馈或 toast。
- 用户点击快捷调优后，能带着原始条件进入再生成流程。
- 再生成生成出的结果能保存到衣橱。
- 单套生成时页面仍然正常，不出现“PK”相关空状态错误。

## 7. 玩法三：分享海报

### 7.1 用户价值

H5 的传播依赖“用户愿不愿意分享”。普通生成图缺少上下文，分享出去不容易让别人理解。分享海报需要把图片、场景、天气、风格标签和品牌感组合成一张可转发卡片。

### 7.2 分享内容

建议海报包含：

- AI 生成穿搭图。
- LOOK 名称。
- 场景 / 天气 / 温度。
- 3-5 个风格标签。
- 一句话穿搭总结。
- CloudWear AI 品牌标识。
- 可选二维码或短链。

### 7.3 首期实现方式

首期优先做轻量方案：

- 结果页图片区域增加品牌角标和天气信息。
- 分享按钮调用浏览器原生 `navigator.share`。
- 下载按钮保存当前图片。
- 页面上展示更完整的海报式 caption。

如果要生成真正的合成海报，可以作为第二阶段：

- 前端用 `canvas` 合成图片。
- 或后端提供海报生成接口。
- H5 下载合成后的海报图。

### 7.4 海报样式建议

移动端海报建议采用 3:4 或 9:16：

- 上方：生成图主体。
- 中部：LOOK 标题和摘要。
- 下方：天气、场景、风格标签、品牌标识。

视觉风格应服务穿搭结果，不做过强装饰。海报上不要堆太多说明文字。

### 7.5 验收标准

- 结果页能明确看到分享入口。
- 不支持系统分享的浏览器能给出明确提示。
- 下载或分享不会影响保存衣橱流程。
- 图片加载失败时页面有明确错误或占位，不伪造成功。

## 8. 页面调整建议

### 8.1 首页

首页建议信息顺序：

1. 品牌和核心价值：AI 智能搭配，发现更适合你的出门 LOOK。
2. 今日穿搭任务：任务卡入口。
3. 生成方式：关键词生成 / 照片换搭。
4. 灵感关键词：运营配置的关键词。
5. 生成流程：输入条件 -> 生成方案 -> 保存衣橱。

关键原则：

- 首页不要像功能说明页，要像可直接开始玩的工具。
- 第一屏必须出现可点击的玩法入口。
- 任务卡和生成方式不能互相抢主行动线。

### 8.2 关键词生成页

保留当前字段，但支持从任务卡带入默认值。

建议增强：

- 展示“来自任务：30 秒通勤不出错”。
- 用户可继续修改带入的条件。
- 自动生成时仍允许用户看到明确进度。

### 8.3 照片换搭页

照片换搭可以增加“换搭模式”：

- 更显瘦。
- 更日常。
- 更高级。
- 更适合拍照。

首期可以先把这些模式拼接进关键词，不需要新增接口。

### 8.4 结果页

结果页建议强化：

- 多套切换区的“第几套 / 共几套”。
- 当前 LOOK 的反馈按钮。
- 快捷调优按钮。
- 保存、下载、分享三个明确操作。

### 8.5 AI 衣橱

AI 衣橱暂不做大改。

可以小幅增强：

- 标识记录来源：关键词生成 / 照片换搭 / 任务卡。
- 支持按场景或风格搜索。
- 从历史详情页继续“生成相似风格”。

## 9. 数据与接口影响

### 9.1 首期最小改造

首期不要求后端改表，也不新增接口。

前端通过以下方式完成：

- 任务卡本地配置。
- URL 参数承接预设条件。
- 现有生成接口继续接收 `OutfitInput`。
- 调优动作拼接到 `style` 字段。
- 分享使用前端能力。

### 9.2 后续可选改造

如果要支持运营配置和长期个性化，建议后续扩展：

1. H5 配置增加 `scenarioTasks`。
2. 生成记录增加 `playMode` 或 `sourceMeta`。
3. 记录用户反馈标签。
4. 风格档案归纳时参考反馈标签。

可能字段：

```ts
type H5PlayMode = "manual" | "scenario_task" | "photo_tune" | "result_tune";

interface SourceMeta {
  playMode: H5PlayMode;
  scenarioTaskId?: string;
  tuneActionId?: string;
  feedback?: string;
}
```

首期不建议立即改数据库，除非明确要做后台统计。

## 10. 配置建议

现有 H5 配置已经包含：

- 首页图。
- 灵感关键词。
- 首页 looks。
- 季节、天气、温度、地点、风格、场景、颜色、单品。
- 图片模型。
- 生成张数。
- 每日免费生成限制。

建议新增配置项：

- `scenarioTasks`：首页任务卡。
- `photoModes`：照片换搭模式。
- `tuneActions`：结果页快捷调优动作。
- `feedbackActions`：结果页反馈按钮。

首期可以先写死前端，等玩法稳定后再迁入后台配置。

## 11. 分阶段实施计划

### 阶段 1：场景任务卡

目标：让首页从“入口页”变成“玩法页”。

改动：

- 新增任务卡配置。
- 首页渲染任务卡模块。
- 点击任务卡生成 URL 参数。
- 登录态和未登录态沿用现有逻辑。
- 验证关键词生成流程不被破坏。

推荐优先级：最高。

### 阶段 2：结果页 PK 和调优

目标：提升生成后的互动深度。

改动：

- 强化多套切换视觉和状态。
- 反馈按钮增加明确选中态或 toast。
- 快捷调优动作继续复用 `buildTuneHref`。
- 单套结果和多套结果都要有合理展示。

推荐优先级：高。

### 阶段 3：分享海报

目标：提升传播和转发。

改动：

- 优化结果图 caption。
- 强化分享按钮和下载按钮。
- 首期使用原生分享和下载。
- 第二阶段再考虑 canvas 合成海报。

推荐优先级：中高。

### 阶段 4：配置化和数据沉淀

目标：支持运营调整和个性化。

改动：

- 后台 H5 配置增加玩法配置。
- 生成记录保留玩法来源。
- 风格档案归纳参考反馈。
- 后台查看任务卡转化和保存率。

推荐优先级：中。

## 12. 验证方案

### 12.1 静态验证

- TypeScript 类型检查。
- ESLint。
- Next.js build。

### 12.2 交互验证

核心路径：

1. 首页点击任务卡。
2. 未登录用户看到登录提示。
3. 登录后回到任务卡对应生成页。
4. 已登录用户点击任务卡后进入关键词生成页。
5. 用户修改预设条件并生成。
6. 多套结果页可切换 LOOK。
7. 点击反馈按钮有明确反馈。
8. 点击快捷调优可以再次生成。
9. 保存到 AI 衣橱成功。
10. 下载或分享不影响保存状态。

### 12.3 移动端验证

至少验证：

- iPhone SE 宽度。
- 常规 iPhone 宽度。
- Android 常见 360px 宽度。

重点检查：

- 任务卡文案不溢出。
- 底部导航不遮挡主按钮。
- 结果页按钮不换行错乱。
- 图片区域和标签不重叠。

## 13. 风险与处理

### 13.1 首页过载

风险：任务卡、生成方式、灵感关键词同时出现，首页可能变得拥挤。

处理：任务卡首期限制 4-6 个首屏展示，更多用横向滚动或折叠，不要一次铺满。

### 13.2 用户误以为任务卡不可修改

风险：用户点击任务卡后以为只能生成固定模板。

处理：进入生成页后展示可编辑条件，并提示“已为你预填，可继续修改”。

### 13.3 调优结果不稳定

风险：把调优动作拼接到 `style` 字段，模型可能理解不一致。

处理：调优 prompt 需要短而明确，避免复杂复合指令。生成失败或不满意时透明展示失败，不做假成功。

### 13.4 分享能力受浏览器限制

风险：部分浏览器不支持 `navigator.share`。

处理：保留下载按钮；不支持分享时提示“当前浏览器不支持系统分享”。

### 13.5 生成成本上升

风险：多套 PK 会鼓励用户生成更多图片。

处理：沿用每日免费生成限制；生成前显示剩余张数；当剩余张数不足时明确提示减少生成张数。

## 14. 推荐首版方案

推荐首版只做三个闭环：

1. 首页新增“今日穿搭任务”。
2. 结果页强化“多套 PK + 快捷调优”。
3. 结果页强化“分享 / 下载海报感”。

不建议首版立刻做复杂风格测试或完整衣橱复盘。它们更适合作为第二轮玩法，因为需要更多问答结构、数据沉淀和个性化策略。

## 15. 后续方向

### 15.1 风格测试

做成 5-7 道轻问答，输出“穿搭人格卡”：

- 松弛通勤型。
- 温柔法式型。
- 清冷极简型。
- 甜酷出片型。
- 运动街头型。

可用于拉新和分享，但需要新增问答页和结果卡。

### 15.2 衣橱复盘

基于历史记录生成：

- 我的高频风格。
- 我的常用色。
- 我的高频场景。
- 我的显瘦关键词。
- 下一套推荐。

适合提升留存，但依赖用户积累足够记录。

### 15.3 运营活动

可围绕节日或场景做短期玩法：

- 五一旅行穿搭。
- 母亲节约会 / 家庭聚餐。
- 毕业季拍照。
- 入职第一周通勤。
- 夏日海边三套。

活动本质上可以复用场景任务卡体系。
