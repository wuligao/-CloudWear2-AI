# CloudWear AI 第一版需求文档

## 1. 产品概述

CloudWear AI 是一个面向移动端优先体验的 AI 穿搭生成应用。用户输入季节、天气、气温、打卡地点和个人风格后，系统生成可参考的穿搭图片与搭配说明，并支持保存历史生成记录。

第一版目标不是做完整虚拟试衣，也不是做复杂衣柜管理，而是验证一个核心问题：用户是否愿意基于真实出行场景使用 AI 生成穿搭方案，并保存、复用这些结果。

## 2. 目标用户

### 2.1 核心用户

- 18-35 岁，有日常穿搭、拍照打卡、通勤、约会、旅行需求的用户。
- 经常在出门前纠结穿什么，希望快速得到搭配灵感的人。
- 喜欢小红书、Instagram、Pinterest 风格参考，但不想反复搜索的人。

### 2.2 典型场景

- 周末去城市街区打卡，希望穿搭适合拍照。
- 工作日通勤，希望根据温度快速生成不出错的搭配。
- 旅行前根据目的地天气生成几套穿搭灵感。
- 约会、展览、咖啡店、海边、雪地等特定场景穿搭参考。

## 3. MVP 范围

### 3.1 必须交付

- 用户可以输入穿搭条件。
- 系统可以生成结构化穿搭方案。
- 系统可以生成穿搭图片。
- 用户可以保存生成记录。
- 用户可以查看历史记录和历史详情。
- 用户可以基于历史记录重新生成相似方案。
- 页面具备加载态、错误态、空态和成功反馈。

### 3.2 暂不交付

- 真人照片换装。
- 精准尺码推荐。
- 电商商品购买链接。
- 社区内容流。
- 评论、点赞、关注。
- 多人穿搭。
- 完整原生 iOS / Android App。
- 复杂会员系统。
- 复杂衣柜管理。

## 4. 核心用户流程

### 4.1 生成穿搭

1. 用户进入首页。
2. 选择或输入季节、气温、天气、地点、场景、个人风格和颜色偏好。
3. 点击生成。
4. 系统展示生成进度。
5. 系统返回穿搭图片、标题、说明、单品列表和适合理由。
6. 用户选择保存或重新生成。

### 4.2 保存历史

1. 用户在生成结果页点击保存。
2. 系统保存输入条件、结构化穿搭方案、图片地址和生成提示词。
3. 用户进入历史页。
4. 用户按时间倒序查看历史记录。
5. 用户点击某条记录进入详情页。

### 4.3 重新生成

1. 用户进入历史详情页。
2. 点击“生成相似风格”。
3. 系统复用该记录的关键条件，并允许用户修改其中部分条件。
4. 系统生成新的穿搭方案和图片。

## 5. 功能需求

### 5.1 首页 / 生成页

输入项：

- 季节：春、夏、秋、冬。
- 气温：数字输入，单位为摄氏度。
- 天气：晴、多云、雨、雪、风大、湿热、寒冷等。
- 地点：城市、街区或目的地，例如“上海武康路”“北京国贸”“三亚海边”。
- 场景：通勤、约会、旅行、咖啡店、展览、户外、校园、晚餐、拍照打卡。
- 个人风格：简约、韩系、日系、法式、通勤、运动、甜酷、复古、街头、轻奢。
- 颜色偏好：可选，例如黑白灰、低饱和、亮色、莫兰迪、冷色、暖色。
- 穿搭倾向：可选，例如女性化、中性、男性化、不限。

操作：

- 点击生成。
- 生成中禁用重复提交。
- 生成失败时展示明确错误信息。

输出：

- 穿搭图片。
- 穿搭标题。
- 一句话摘要。
- 单品列表。
- 场景适配理由。
- 温度适配说明。
- 风格标签。
- 保存按钮。
- 重新生成按钮。

### 5.2 历史页

展示内容：

- 历史记录列表。
- 每条记录展示缩略图、标题、地点、温度、风格、创建时间。
- 空态提示用户先生成第一套穿搭。

操作：

- 查看详情。
- 删除记录。

### 5.3 历史详情页

展示内容：

- 大图。
- 原始输入条件。
- 穿搭标题。
- 穿搭说明。
- 单品列表。
- 生成时间。

操作：

- 生成相似风格。
- 删除记录。
- 返回历史列表。

### 5.4 个人风格页

第一版只做轻量配置：

- 常用风格。
- 喜欢颜色。
- 避免颜色。
- 常用场景。
- 自定义备注，例如“不喜欢太夸张”“希望显高”“偏通勤”。

如果第一版工期紧，可以先隐藏个人风格页，将风格偏好直接放在生成页表单中。

## 6. AI 生成需求

### 6.1 结构化穿搭方案

关键词生成应优先直接根据用户输入拼接图片提示词，减少一次文本模型调用。上传照片生成可先通过大语言模型生成结构化 JSON，再生成图片。结构化结果包含：

- outfitTitle
- summary
- styleTags
- temperatureAdvice
- occasionReason
- items
- imagePrompt

上传照片生成的 items 至少包含：

- category
- name
- color
- material
- reason

### 6.2 图片生成要求

图片应体现：

- 完整穿搭效果。
- 明确季节和温度感。
- 与地点或场景相符。
- 与用户风格偏好一致。
- 避免文字、水印、品牌商标。
- 第一版默认生成单人全身穿搭图。

### 6.3 生成限制

- 第一版每次只生成 1 套穿搭，降低成本和等待时间。
- 后续可扩展为一次生成 3 套。
- 生成过程需要展示进度和等待提示。
- 对明显违法、色情、暴力、未成年人性化、仇恨等内容拒绝生成。

## 7. 数据需求

### 7.1 生成记录

每次生成必须保存可追溯信息：

- 用户 ID 或匿名会话 ID。
- 用户输入条件。
- LLM 结构化输出。
- 图片生成提示词。
- 图片 URL。
- 创建时间。

### 7.2 用户偏好

第一版可以保存轻量偏好：

- 风格偏好。
- 颜色偏好。
- 避免项。
- 常用场景。
- 备注。

## 8. 非功能需求

### 8.1 性能

- 首页首屏在正常网络下应尽快可交互。
- 单次生成目标控制在 30-60 秒内。
- 生成中需要明确反馈，避免用户误以为页面卡死。

### 8.2 可用性

- 移动端优先。
- 表单输入尽量用选择项，减少用户输入成本。
- 结果页信息清晰，不堆过长解释。

### 8.3 安全与隐私

- 第一版不要求上传真人照片，降低隐私风险。
- 所有用户输入需要服务端校验。
- API Key 只保存在服务端环境变量中。
- 历史记录只允许当前用户或当前匿名会话访问。

### 8.4 成本控制

- 限制匿名用户每日生成次数。
- 服务端记录生成次数。
- 失败请求不应重复扣减用户可用次数，除非图片服务已实际产生计费。

## 9. 验收标准

- 用户可以完成一次穿搭生成。
- 生成结果包含图片、标题、摘要、单品列表和适配理由。
- 用户可以保存生成结果。
- 用户可以在历史页看到保存记录。
- 用户可以进入历史详情页查看完整信息。
- 用户可以删除历史记录。
- 移动端主要页面无明显布局错位。
- 生成失败时有明确错误提示。
- API Key 不出现在前端代码或浏览器响应中。

## 10. 第一版成功指标

建议在试用阶段重点观察：

- 生成完成率。
- 生成后保存率。
- 历史页访问率。
- 相似风格重新生成率。
- 7 日内重复使用人数。
- 用户主观反馈：是否觉得“真的能参考穿”。

## 11. 后续扩展方向

- 一次生成 3 套方案。
- 天气 API 自动获取当地天气。
- 用户上传参考风格图。
- 真人照片试穿。
- 衣柜管理。
- 电商商品匹配。
- 分享海报。
- 风格记忆和长期偏好学习。
- 会员订阅和高清图生成。
